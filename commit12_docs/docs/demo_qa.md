# 期末發表：Demo 腳本與 Q&A 題庫

| 段落 | 時間 | 重點 |
|---|---|---|
| 1. 背景與需求 | 1.5 分 | 學生排隊、店家剩食；目標使用者：學生、學餐店家、總務處 |
| 2. AI 技術與架構 | 2.5 分 | 兩個模型、特徵、時間切分、分位數迴歸、LLM 只負責說明 |
| 3. 系統 Demo | 4 分 | 照下面的腳本操作 |

## 二、Demo 腳本（4 分鐘）

> 數字以你們電腦實際跑出的結果為準（`python -m foodcast.train`、`python -m foodcast.tuning`）。
>
> 上台前：先執行一次 `streamlit run app.py`，讓模型訓練完成；另外錄一支備援影片，網頁出問題時直接播。

1. **首頁**（20 秒）：指著四個 KPI，一句話講完成果，並說明「目前用模擬資料驗證方法」。
2. **學生人潮預報**（60 秒）
   - 唸出推薦卡片：「明天午餐推薦幾點去、12:00 尖峰大約幾人。」
   - 把**雨量拉到 20 mm** →「下雨天少人外出，人潮上升。」指著卡片下方的 💡：「系統會說明原因，下雨讓人數增加了多少。」
   - 日期換到**期末考週** →「晚餐尖峰往後移，因為大家讀完書才去吃。」
3. **店家備餐建議**（70 秒）
   - 服務水準 70% → 90%：「越保守，建議量越多。」
   - 指著取捨曲線：「每個藍點都在紅叉的左上方：剩食更少、賣完的情況也更少。」
   - 選「今日特餐：咖哩飯」→ 咖哩飯建議量上升。
   - 往下捲，展示**未來 7 天備餐計畫**，可以下載給店家進貨。
4. **成效報告**（30 秒）：「換算成金額，測試期間約省下多少錢」；指出最省錢的服務水準和我們選 70% 的理由。
5. **模型分析**（40 秒）：模型比較長條圖，線性迴歸比基準線還差，原因是非線性；超參數調整的結論；錯誤分析指出模型在假日、下雨天比較不準。
6. **上傳真實資料**（20 秒）：「學餐給我們 POS 資料，上傳後就能直接重新訓練。」打開範本給評審看。
7. **AI 助理**（30 秒）：點「明天中午幾點去人最少？」

## 三、Q&A 題庫

**資料與可信度**

1. **Q：資料是真的嗎？**
   A：是模擬資料。我們拿不到學餐的銷售紀錄，所以依照明確的假設產生資料（假設都寫在 `data_generator.py`），先驗證整套流程。系統已經做好「上傳真實資料」功能，拿到 POS 資料就能直接重新訓練。

2. **Q：用模擬資料訓練，模型不就只是學會你們自己設定的規則？**
   A：沒錯，這是最大的限制。所以 63.6% 代表「方法可行」，不代表實際成效。模擬資料的價值在於驗證「時間切分、分位數備餐、回測」這套流程是正確的。換成真實資料，流程完全不用改。

3. **Q：「目前備餐方式」是怎麼來的？會不會故意設得很差？**
   A：我們假設店家參考前兩週同一天的銷量再多備 15%，這是常見的經驗做法。它的問題是看不到行事曆和天氣，所以連假、考試週前後最容易出錯。

**模型**

4. **Q：為什麼選梯度提升樹？**
   A：我們比較了 4 種方法，梯度提升樹的 MAE 最低（16.9 人），R² 0.956。人潮和時段、星期幾是非線性關係，還有交互作用（例如考試週 × 晚餐），樹模型可以自動學到。

5. **Q：為什麼線性迴歸比「歷史平均」還差？**
   A：線性迴歸假設「時段每增加 1 小時，人數固定增加 X 人」，但實際上 12:00 是尖峰、前後都比較少，是山形的。它把「時段」當成一條直線，所以預測得很差。

6. **Q：資料怎麼切訓練集和測試集？為什麼不隨機切？**
   A：依時間切：2026/3/1 之前訓練，之後測試。隨機切會用未來的資料預測過去，分數會太樂觀，實際上線時根本拿不到未來的資料。

7. **Q：有做交叉驗證或調參數嗎？**
   A：有。我們用以「日期」為單位的時間序列交叉驗證，試了 27 組超參數。CV 最佳的組合在測試集反而沒有比較好，而且 CV 差距比各 fold 的標準差還小，所以判斷是隨機波動，維持原本設定，避免過度調參。

8. **Q：分位數迴歸是什麼？為什麼不直接預測平均值？**
   A：一般迴歸預測「平均會賣幾份」，但如果剛好準備平均值，大約有一半的日子會賣完。分位數迴歸預測「有 70% 的機率需求不會超過幾份」，店家可以自己選要多保守。這是機器學習加上「報童問題」的做法。

9. **Q：哪些因素影響最大？**
   A：置換重要性顯示用餐時段、星期幾影響最大，其次是國定假日、是否學期中、雨量。

10. **Q：模型會不會過擬合？**
    A：我們全程用模型沒看過的測試期間（122 天）評估，R² 仍然有 0.956；也比較了基準線。交叉驗證的結果也支持目前的設定沒有過度調參。

**AI 與系統**

11. **Q：AI 助理是 ChatGPT 嗎？數字會不會亂講？**
    A：數字一律來自我們自己訓練的模型。有 API 金鑰時，LLM 只負責把結果講成口語，System Prompt 規定不可以自己估算數字；沒有金鑰時用離線模式，Demo 不受影響。

12. **Q：天氣資料從哪來？**
    A：目前要手動輸入氣象預報，預設是該月平均氣溫。未來可以串接中央氣象署的開放資料 API。

13. **Q：減碳 25.8 噸怎麼算的？**
    A：剩食減少的公斤數 × 每公斤廚餘約 2.5 kg CO₂e 的估計值。這只是用來呈現量級，不是精確的碳盤查。

**應用與未來**

14. **Q：店家真的會用嗎？**
    A：店家每天只需要看一張建議表，還能下載 7 天計畫安排進貨，操作很簡單。下一步想先找一間學餐試用一個月，比較實際的剩食量。

15. **Q：跟現有的排隊 App 有什麼不同？**
    A：一般 App 顯示「現在」幾個人；我們預測「未來」的人潮，而且同時服務學生和店家，從源頭減少剩食。

16. **Q：最大的困難是什麼？**
    A：拿不到真實資料。我們的解法是用明確的假設模擬資料，同時做好上傳真實資料的功能，讓系統可以無痛換成真實資料。

**新功能**

17. **Q：「為什麼明天人比較多」是怎麼算出來的？**
    A：用反事實比較：把下雨、考試週這些因素一個一個改回一般狀態，再預測一次，兩次的差距就是該因素的影響。這種方法不用打開模型內部，任何模型都能用。

18. **Q：省下的錢怎麼算？**
    A：剩食損失（剩下的份數 × 食材成本）加上缺貨損失（沒賣到的份數 × 毛利），兩種都算才公平。成本和售價是估計值，可以換成店家的真實數字。

19. **Q：模型什麼時候最不準？**
    A：錯誤分析顯示，國定假日、寒暑假這類人少的日子相對誤差最高，而且測試期間這種日子很少；整天誤差最大的日子多半有下雨或考試週。改善方向是更精確的天氣資料，以及用學生回報即時修正。

20. **Q：學生回報的資料有什麼用？**
    A：一是檢查預測準不準（預測「舒適」但學生說大排長龍，就代表有問題）；二是累積成真實資料，未來可以拿來重新訓練。
